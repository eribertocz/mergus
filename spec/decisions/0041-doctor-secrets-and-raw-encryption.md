# 0041 · mergus doctor for secrets, and raw encrypted by DuckLake

- Status: accepted
- Date: 2026-11-26
- Answers: the last two phase 0.3 rules without an issue (MG-REQ-1004, MG-REQ-0515)

## Context

MG-REQ-1004 named `mergus doctor` without saying what it lists or how it fails. MG-REQ-0515
said "keys from `security/`", but DuckLake manages its own keys.

Verified facts (https://ducklake.select/docs/stable/duckdb/advanced_features/encryption,
DuckLake 1.1, released with DuckDB 2.0):

- Encryption is chosen with the `ENCRYPTED` attach option when the catalog is set up. The mode
  "is persisted in the catalog", and asking for a different mode on an existing catalog "is
  rejected".
- "The encryption keys for each file are automatically generated by the system when the files
  are written." They are 256-bit and stored in the catalog (`ducklake_data_file` and
  `ducklake_delete_file`, column `encryption_key`). The random generator is "provided by the
  httpfs extension".
- Reading needs no extra key: "the keys are read from the catalog server".
- Parquet data and delete files are encrypted; the page does not say the catalog is.

## Decision

- `mergus doctor` (phase 0.3) lists each secret reference of the sources with its origin,
  never a value, and reports missing ones as `MG-1003`. Its `--json` events follow the other
  read commands.
- Raw is a DuckLake catalog created `ENCRYPTED`. The keys live in the catalog, so the catalog
  is protected as a secret: raw-zone credentials, and never a local file inside the project
  folder. An unencrypted existing raw catalog is refused.
- `httpfs` joins the extensions MG-REQ-0194 may install, only for this purpose.

## Consequences

- No key management in Mergus for raw; losing the catalog loses the keys, as it loses the data.
- `doctor` grows with later phases (`--source`, `--security`, `--network`).
